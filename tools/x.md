# Posting on X as @laserstackphp

`tools/x` posts, replies and reads on X through
[twitter-cli](https://github.com/jackwener/twitter-cli), authenticated with the
session cookie of @laserstackphp. The record of the account is one 1Password
item, **Laser Stack X**, in the **Personal** vault:

| Field | Value |
|---|---|
| username | `laserstackphp` |
| password | generated by 1Password, 32 characters; nothing else holds it |
| recovery email | `laserstack@bruder.com.br`, a Workspace alias that delivers to the main inbox |
| one-time password | the two-factor seed, added at signup |
| `auth_token`, `ct0` | two text fields, the session cookie `tools/x` posts with |
| notes | the recovery codes, written when X shows them |

The email is an alias on a domain that stays: a mailbox you control outlives
any provider. That alias, the seed and the codes are the way back in —
@laserstack_sdb was lost because none of them was written down.

`~/.laserstack-x`, mode 600, is the fallback for a machine without 1Password. It
holds the handle and the email, and can hold the same cookie on two
`TWITTER_AUTH_TOKEN` and `TWITTER_CT0` lines. `tools/x` tries the environment,
then the item, then that file.

## Do not deploy the site before the account exists

The site and the README already name @laserstackphp. Until the handle resolves,
the Community footer of every page links a 404 profile. Create the account
first, then redeploy the site.

## Why not the official API

X removed the free API tier on 2026-02-06. Access is pay per use, from prepaid
credits in the Developer Console:

| Action | Price |
|---|---|
| Post | $0.015 |
| Post with a link | $0.200 |
| Read one post | $0.005 |

The link surcharge is 13 times the price of a plain post, and most posts of this
project carry a link: 300 link posts a month cost $60. `twitter-cli` sends the
same GraphQL requests as the web app, with the cookie of the account, so a post
costs nothing.

## Risk

Automating a web session is against the X terms of service. X can rate-limit,
lock or suspend the account. That is why the project has its own handle: the
damage stops at @laserstackphp and never reaches the personal account.

Keep the account within human behavior: a few posts, no bulk follow or unfollow,
no direct messages, no bursts. An unverified account may create about 50 posts
and 200 replies a day, inside a 30-minute burst window that X does not publish.

The cookie is a password. `auth_token` gives full control of the account until
that session ends.

## Create the account, once

1. In Chrome, open the profile menu, choose **Add**, and make a profile named
   `laserstackphp`. Sign in to x.com as this account only, in that profile.
2. Open 1Password, item **Laser Stack X**, and copy the password from there into
   the signup form. Do not retype it and do not write it anywhere else.
3. Sign up at <https://x.com/i/flow/signup> with `laserstack@bruder.com.br`.
4. Click the verification link that arrives at the alias.
5. Two-factor: **Settings** → **Security and account access** → **Security** →
   **Two-factor authentication** → **Authentication app**. Do not choose SMS:
   the phone number is the part that goes stale. Show the QR code and add it to
   the item's **one-time password** field.
6. **Settings** → **Two-factor authentication** → **Recovery code**. Put the
   codes in the notes of the item.

## Store the cookie, once

1. In that browser, open <https://x.com>, then DevTools (⌥⌘I) → **Application** →
   **Cookies** → `https://x.com`.
2. Copy the values of `auth_token` and `ct0`.
3. In the item, add two **text** fields named exactly `auth_token` and `ct0`, and
   paste the values. The names are what `tools/x` reads; another name reads as an
   empty cookie.
4. Check both, then the account:

   ```sh
   op read 'op://Personal/Laser Stack X/auth_token' | wc -c   # not 0
   tools/x whoami                                             # @laserstackphp
   ```

## Install, once

```sh
uv tool install twitter-cli
```

The 1Password CLI needs the desktop app integration on: **1Password** →
**Settings** → **Developer** → **Connect with 1Password CLI**, so that
`op read 'op://Personal/Laser Stack X/username'` prints `laserstackphp` without
a separate sign-in. Run `uv tool upgrade twitter-cli` when a request starts to
fail: X changes the web app often, and the tool follows it.

## Use

```sh
tools/x whoami                          # must print @laserstackphp
tools/x post "Laser Stack 2.0 is out"    # a post
tools/x post "text" -i docs/og.png       # with an image, up to four
tools/x reply <tweet-id> "text"
tools/x quote <tweet-id> "text"
tools/x delete <tweet-id>
tools/x feed --max 20                    # home timeline of that account
tools/x user-posts laserstackphp --max 20
tools/x search "laserstack" -t Latest
```

Add `--json` or `--yaml` for scripts. `twitter --help` lists every command;
`tools/x` passes all of them through.

`tools/x` looks for the cookie in this order: `TWITTER_AUTH_TOKEN` and
`TWITTER_CT0` in the environment, then the 1Password item, then
`~/.laserstack-x`. When none of the three answers, the wrapper stops instead of
letting `twitter-cli` extract the cookies of whichever browser it finds.

Then, before the command runs, the wrapper calls the verification endpoint of X
with those two values and nothing else, and stops unless the answer is
`laserstackphp`. That is not ceremony: `twitter-cli` re-extracts the cookies of
the browser when its own verification fails, so a stale cookie would otherwise
post as whichever account the browser holds. The check costs one cheap request
and closes that path.

## When it breaks

| Message | Cause | Fix |
|---|---|---|
| `Cookie expired or invalid (HTTP 401)` | the session ended | repeat **Store the cookie** |
| `the cookie authenticates as '…', not as @laserstackphp` | the cookie is stale, belongs to another account, or the account could not be read | copy both values again from the browser session of @laserstackphp |
| `Couldn't get KEY_BYTE indices`, or a transaction-id error | X changed its web app | `uv tool upgrade twitter-cli` |
| `no usable cookie in op://Personal/...` | vault locked, the field names differ, or no source has a cookie | `op read 'op://Personal/Laser Stack X/ct0'` must print a value |
| `no account found for filter` from `op` | the CLI lost the desktop app integration | turn the integration on again, or fill `~/.laserstack-x` |
| a post gone out from the wrong account | never possible here: the cookie names the account | `tools/x whoami` |

## If the account is lost again

1. **Password**: <https://x.com/i/flow/password_reset>, enter `laserstackphp`,
   use the link that arrives at `laserstack@bruder.com.br`, then choose
   **Try another way / Use email instead** if login asks for a phone.
2. **Two-factor**: the seed is in the item, the recovery codes in its notes.
3. A live browser session still works while its cookie lives: copy `auth_token`
   and `ct0` and skip the reset entirely.
